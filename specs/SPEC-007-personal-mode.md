# SPEC-007 — Personal mode

## 1. Summary
بسیاری از کاربران (و خودِ مالک پروژه) می‌خواهند Konklancer را **برای خودشان** اجرا کنند: روی
کامپیوتر خودشان، با اسکنی که برای سلیقه‌ی خودشان انجام می‌شود. `SPEC-004` زیرساخت فید را تعریف کرده
بود اما پیکربندی/زمان‌بندی/مسیرهای جایگزین جمع‌آوری داده را مشخص نکرده بود. این سند همان شکاف را
پر می‌کند و دو اصل را قفل می‌کند: **صداقت داده** و **فقط‌خواندنی بودن**.

> وضعیت: DRAFT — پیاده‌سازی این سند انجام شده است (به درخواست مالک پروژه)، اما برای رسمی‌شدن نیاز به
> تأیید صریح دارد (طبق AGENTS.md بخش ۲).

## 2. Behavioral Contract

### 2.1 پیکربندی اسکن (env-only، بدون فایل تنظیمات جدید)
- R1. پیکربندی اسکنر از محیط خوانده می‌شود: `KONKLANCER_SCAN_PLATFORMS`, `KONKLANCER_SCAN_TELEGRAM`,
  `KONKLANCER_SCAN_INCLUDE`, `KONKLANCER_SCAN_EXCLUDE`, `KONKLANCER_SCAN_PAGES`,
  `KONKLANCER_SCAN_DELAY`, `KONKLANCER_SCAN_MIN_SCORE`, `KONKLANCER_SCAN_INTERVAL_MIN`,
  `KONKLANCER_PROJECTS_FILE`, `KONKLANCER_PYTHON`, `KONKLANCER_SCAN_TIMEOUT_MS`.
- R2. اگر هیچ منبعی پیکربندی/فعال نشده باشد، اسکن با پیام راهنما رد می‌شود (نه با خطای مبهم) و UI
  خالی می‌ماند.
- R3. هر اجرای اسکن با قفل درون‌فرایندی محافظت می‌شود؛ دو اسکن هم‌زمان ممکن نیست.

### 2.2 زمان‌بندی
- R4. `KONKLANCER_SCAN_INTERVAL_MIN > 0` یعنی اسکن خودکار دوره‌ای؛ پیش‌فرض خاموش است. هرگز در
  راه‌اندازی اول اجرا نمی‌شود (کاربر باید آگاهانه شروع کند).

### 2.3 مسیرهای جمع‌آوری داده (به ترتیب ایمنی)
- R5. **مسیر مرورگر:** کاربر صفحه را خودش در مرورگر ذخیره می‌کند و
  `parse-file --out` / `parse-telegram-file --out` رکوردها را در فید JSONL می‌نویسند. این مسیر هیچ
  درخواست خودکاری به سایت نمی‌فرستد و نباید حذف شود.
- R6. **مسیر اسکن خودکار:** `scan --platform/--telegram` طبق `scanner/README.md`، فقط منابعی که
  `scan_enabled=true` (و برای پلتفرم‌ها `scan_selectors`) دارند.
- R7. فعال/غیرفعال‌کردن منابع با `enable`/`disable` انجام می‌شود؛ `enable --platform` بدون
  `scan_selectors` رد می‌شود.
- R8. `fetch_html` علت توقف را تفکیک می‌کند: منع صریح `robots.txt`، خطای ۵xx میزبان، و خطای شبکه.
  در هر سه حالت آن میزبان برای همان اجرا کنار گذاشته می‌شود (fail-closed طبق RFC 9309).

### 2.4 صداقت در UI و API
- R9. `GET /api/jobs` فیلد `source` می‌دهد: `scanner` (داده‌ی واقعی) | `demo` (ساختگی، فقط با
  `KONKLANCER_DEMO=1`) | `empty`.
- R10. UI پیش‌فرض هیچ پروژه‌ی ساختگی نشان نمی‌دهد؛ داده‌ی ساختگی فقط در حالت دمو و با برچسب صریح
  نمایش داده می‌شود. هیچ «پروژه‌ی تکمیل‌شده‌ی» جعلی برای پر کردن نمودار درآمد تزریق نمی‌شود.
- R11. `/api/bridge/status` فقط منابع فعال را گزارش می‌کند و هیچ latency ساختگی نمی‌سازد.
- R12. هر پروژه در فید `url` (لینک صفحه‌ی اصلی)، `score` (۰ تا ۱۰۰) و `scoreReasons` دارد تا کاربر
  بداند چرا این پروژه بالا آمده است.
- R13. پوش پروژه‌های تازه بر پایه `id` یکتاست؛ پروژه‌های تکراری دوباره پوش نمی‌شوند (SPEC-004 R2).

### 2.5 پیش‌فیلتر
- R14. امتیاز پیش‌فیلتر کاملاً قاعده‌محور است (بودجه، تعداد پیشنهاد، تازگی، هم‌پوشانی کلیدواژه، تناسب
  دسته با AI) و پیش از هر `callLLM` اجرا می‌شود (SPEC-004 R5 و SPEC-006 R8).
- R15. `KONKLANCER_SCAN_MIN_SCORE` آستانه‌ی ورود به فید را تعیین می‌کند.

### 2.6 دامنه‌ی کار: هر چیزی که AI می‌تواند تولید کند (۲۰۲۶-۱۰-۱۲)
- R16. اسکنر و فید به کار کدنویسی/ربات محدود نیستند. `shared/taxonomy.json` منبع واحد دسته‌ها است
  (ترجمه، گرافیک/لوگو/بروشور، تصویر/روتوش، ویدیو/انیمیشن، صدا/گویندگی، اسناد/پاورپوینت، محتوا/نویسندگی،
  مارکتینگ/سئو، داده/اکسل، رابط کاربری، اتوماسیون/ربات، وب/اپلیکیشن، «سایر») و هر سه لایه (اسکنر Python،
  سرور، UI) از همان فایل می‌خوانند.
- R17. **هیچ فیلتر پیش‌فرضی وجود ندارد.** خالی‌بودن `include` و `categories` یعنی همه‌ی دسته‌ها خوانده و
  در فید نوشته می‌شوند؛ حذف فقط با `KONKLANCER_SCAN_EXCLUDE` یا `KONKLANCER_SCAN_CATEGORIES` (محدودکردن
  صریح) رخ می‌دهد. کلیدواژه‌ی بی‌مطابقت پروژه را حذف نمی‌کند (امتیاز خنثی می‌گیرد).
- R18. هر رکورد فید فیلد `category` دارد (کلید تاکسونومی) و UI برچسب فارسی و فیلتر همان دسته‌ها را از
  همان منبع می‌سازد؛ فهرست دسته در سرور و UI هاردکد نمی‌شود.

### 2.7 اسکن واقعی و خودکالیبراسیون (۲۰۲۶-۱۰-۱۲)
- R19. اسکن باید داده‌ی زنده‌ی واقعی استخراج کند؛ هیچ داده‌ی ساختگی/ماک در مسیر پیش‌فرض نیست و
  شکست‌ها صریح و قابل‌تشخیص گزارش می‌شوند (robots، خطای شبکه، صفحه‌ی JS-محور).
- R20. `scanner/autoparse.py` ساختار فهرست را از خود HTML کشف می‌کند (گروه‌های هم‌امضا و هم‌فرند،
  تفکیک ستون با `:nth-of-type`، نرمال‌سازی ارقام فارسی) و فیلدهای عنوان/لینک/بودجه/پیشنهاد/زمان را
  انتخاب می‌کند.
- R21. سه لایه‌ی اجرا وجود دارد: ① `autoscan` (صفحه‌ی زنده + کشف خودکار + نوشتن فید)،
  ② `probe --save` (تأیید نامزدها و ماندگارکردن انتخابگر)، ③ `autoscan --html` / `autodetect --html`
  (HTML ذخیره‌شده در مرورگر، بدون هیچ درخواست خودکار).
- R22. `scan --auto` پیش‌فرض سرور است: پلتفرمی که انتخابگر ذخیره‌شده ندارد، در زمان اسکن خودکار
  کالیبره می‌شود؛ `KONKLANCER_SCAN_AUTO=0` این رفتار را خاموش می‌کند.
- R23. انتخابگرها/نامزدهای بدون تأیید زنده در مستندات و کد «تأییدنشده» علامت‌گذاری می‌شوند؛
  هیچ ادعای تأییدشده بودن بدون اجرای واقعی روی صفحه‌ی زنده مجاز نیست.

## 3. Acceptance Criteria
- AC-1: Given `scanner/out/projects.jsonl` با ۳ خط، when `GET /api/jobs`، then `source: "scanner"` و
  فقط پروژه‌های عبورکرده از فیلتر/آستانه با `url` و `score` برمی‌گردند.
- AC-2: Given فایل فید خالی و `KONKLANCER_DEMO=0`، when UI باز می‌شود، then هیچ پروژه‌ی ساختگی دیده نمی‌شود.
- AC-3: Given `KONKLANCER_SCAN_TELEGRAM=1` ولی هیچ کانالی فعال نیست، when trigger-scan، then
  پاسخ ۵۰۲ با پیام راهنمای روشن (بدون اجرای اسکن).
- AC-4: Given یک منبع فعال، when `POST /api/bridge/trigger-scan`، then اسکنر CLI اجرا می‌شود،
  پروژه‌های تازه با `job:new` پوش می‌شوند و `scan:done` با تعداد جدیدها می‌آید.
- AC-5: Given اجرای دوباره‌ی اسکن بدون داده‌ی تازه، then هیچ پروژه‌ی تکراری پوش نمی‌شود.
- AC-6: Given robots.txt میزبان خطای شبکه بدهد، when اسکن، then پیام «خوانده نشد (خطای شبکه)» و
  کنارگذاشتن آن میزبان — نه پیام گمراه‌کننده‌ی «ممنوع کرده است».
- AC-7: Given `parse-file --out FILE`، when اجرا، then رکوردها به فید اضافه و اجرای دوباره بی‌اثر است.
- AC-8: Given فایل فید با پروژه‌های ترجمه/گرافیک/ویدیو و بدون هیچ فیلتر، when `GET /api/jobs`، then
  همه‌ی آن‌ها با `category` درست برمی‌گردند (`categoryFilter: "all"`).
- AC-9: Given `KONKLANCER_SCAN_CATEGORIES="graphic"`، when `GET /api/jobs`، then فقط پروژه‌های گرافیکی
  برمی‌گردند و `categoryFilter: "explicit"` گزارش می‌شود.
- AC-10: Given صفحه‌ی فهرست واقعی (یا HTML ذخیره‌شده‌ی آن) با کارت‌های پروژه، when `autoscan --html`،
  then آیتم‌ها با بودجه/پیشنهاد درست استخراج و در فید نوشته می‌شوند (تست‌های `test_autoparse.py`).
- AC-11: Given صفحه‌ای که فقط با JS پر می‌شود، when `autoscan`، then صفر مورد با پیام روشن «ساختار
  تشخیص داده نشد؛ از --html استفاده کنید» — نه داده‌ی جعلی.
- AC-12: Given کلیدواژه‌ی بی‌مطابقت در `include`، when امتیازدهی، then پروژه حذف نمی‌شود و امتیاز
  خنثی + دلیل «کلیدواژه‌ی دلخواه مطابقت نداشت» می‌گیرد.

## 4. Non-goals
- احراز هویت چندکاربره، حساب کاربری، استقرار ابری (SPEC-003 R5 و آینده).
- ذخیره‌سازی نرخ برد/نتیجه‌ی پیشنهاد (SPEC-005).
- هرگونه ارسال خودکار پیشنهاد، ورود به حساب یا دور زدن محدودیت سایت‌ها (همیشه ممنوع).

## 5. Open Questions
- Q1. تأیید این سند (و در نتیجه تغییر رفتار پیش‌فرض UI از «داده‌ی نمونه» به «فید واقعی خالی»)؟
- Q2. آیا اسکن دوره‌ای باید در UI قابل تنظیم باشد (به‌جای فقط env)؟

## R8 — دسته‌بندی فقط سطح داده است (نه فیلتر پنهان)

- مجموع دسته‌ها شامل کارهای غیرکدنویسی است: ترجمه، گرافیک، ویدیو، صدا، تولید محتوا، مارکتینگ،
  طراحی UI/UX، مستندسازی، داده، اتوماسیون، توسعه و «سایر» (۱۲ + سایر) در `shared/taxonomy.json`.
- **نباید** هیچ فیلتری به‌صورت پیش‌فرض پروژه‌های غیرکدنویسی را حذف کند؛ `include` خالی یعنی
  «همه‌چیز نوشته شود» و محدودسازی دسته فقط وقتی اعمال می‌شود که صریحاً خواسته شود
  (`KONKLANCER_SCAN_CATEGORIES`).
- وقتی `include` پر است و هیچ کلیدواژه‌ای نمی‌خورد، امتیاز کلیدواژه «خنثی» (+۸) است تا پروژه
  حذف نشود ولی امتیاز بالاتری هم نگیرد.

## R9 — کشف خودکار ساختار و کالیبراسیون‌پذیری

- برای سایت‌هایی که انتخابگر CSS ثبت‌شده ندارند، `autoscan` ساختار کارت‌های پروژه را از خود HTML
  کشف می‌کند، انتخابگرها را ذخیره می‌کند (در `platforms.json`) و گزارش می‌دهد.
- انتخابگر درست باید **دقت** داشته باشد: از انتخابگرهای بیش‌ازحد کلی (`div > div`) که منو/فوتر را
  هم می‌گیرند پرهیز می‌کند (جریمه‌ی نسبت تطبیق سراسری در `autoparse`).
- هر ردیف فید باید دو گارد را رد کند: (`_looks_like_nav_item`) و الگوی مسیر پروژه‌ی همان پلتفرم
  (`project_path_pattern`)؛ دستور `prune` همین دو قاعده را روی فید ذخیره‌شده هم اعمال می‌کند.

## R10 — اجرای ابری (برای کسی که کامپیوتر/شبکه‌ی آزاد ندارد)

- همان اسکنر واقعی می‌تواند روی رانرهای GitHub Actions اجرا شود (`.github/workflows/scanner-feed.yml`)
  و فید/وضعیت را در `scanner/cloud-feed.jsonl` و `scanner/cloud-status.json` منتشر کند.
- API سرور: `GET /api/bridge/cloud`، `POST /api/bridge/sync-feed`، `POST /api/bridge/cloud-scan`
  و در UI دو دکمه‌ی «همگام‌سازی» و «اسکن ابری».
- در محیط‌هایی که `fetch` نود به گواهی TLS سفارشی گیر می‌کند، ارتباط با GitHub باید از طریق CLI
  رسمی (`gh api`) ادامه پیدا کند و روش استفاده‌شده (fetch/gh) در پاسخ `/api/bridge/cloud` گزارش شود.
- هیچ داده‌ی ساختگی جایگزین نمی‌شود: اگر اجرای ابری شکست بخورد، وضعیت و متن خطا نشان داده می‌شود.
